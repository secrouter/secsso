# SecSSO — Control Validation

SecSSO is a **thin wrapper around upstream [Authentik](https://goauthentik.io)**: a set of
declarative blueprints (`blueprints/*.yaml`), a Compose topology (`compose.yaml`), and a
control helper (`bootstrap/secsso.sh`). It has no application code of its own — every
identity control below is either (a) a feature Authentik itself implements, upstream, or
(b) a specific configuration this repo's blueprints apply on top of a stock Authentik
install. This document keeps those two sources apart so nothing here is overclaimed as
"SecSSO enforces X" when the enforcement actually lives in Authentik or in a downstream
component (SecRouter, SecChat).

Audit for the identity layer **is** Authentik's own event log (`authentik_events.event`) —
SecSSO does not add a second audit trail. See [AU — Audit & Accountability](#33-audit--accountability-au)
for what that upstream log does and does not provide.

Legend: **Upstream** = an Authentik feature, configurable but not modified by this repo ·
**Wrapper** = a blueprint/compose setting in this repo that configures or extends it ·
**Gap** = not covered here, listed so it isn't silently assumed.

## 3.5 Identification & Authentication (IA)

| Family | Control | Requirement | Implementation | Evidence |
|---|---|---|---|---|
| IA | 3.5.1 / 3.5.2 | Identify & authenticate users, processes, devices | **Upstream** — Authentik's user directory + configurable authentication flow (login, password, and optional MFA stages) authenticates every human sign-in. **Wrapper** additionally provisions distinct non-person-entity (NPE) identities per integration instead of one shared credential: a public device-authorization client for `secagent login` (`blueprints/secagent-pi.yaml`, `client_id: secagent-pi`), and confidential `client_credentials` service identities for secagent's and SecChat's headless calls (`blueprints/secagent-service.yaml`, `blueprints/secchat-service.yaml`) | Authentik admin → Directory → Users; `blueprints/secagent-pi.yaml`, `blueprints/secagent-service.yaml`, `blueprints/secchat-service.yaml` |
| IA | 3.5.3 | **Multifactor authentication** | **Upstream** — Authentik supports TOTP, WebAuthn/security-key, and duo-style MFA stages configurable on the authentication flow (see Authentik's own Stages documentation; this repo does not pin or require a specific MFA method). **Downstream** — the resulting `amr`/`acr` claims are what SecRouter's `requireMfa` gate actually checks; see [Suite integration](#suite-integration) | Authentik admin → Flows & Stages → `default-authentication-flow`; consumption at `work/secrouter/src/security/identity/oidc.ts` (`OidcProvider.authenticate`) |
| IA | 3.5.4 | Replay-resistant authentication | **Upstream** — short-lived signed OIDC tokens (JWT) over TLS, standard OAuth2/OIDC token lifetimes | Authentik admin → Providers → token/refresh lifetimes |
| IA | 3.5.7 / 3.5.10 | Password complexity / cryptographically-protected secrets | **Upstream** — Authentik's configurable password policies and hashed credential storage. **Wrapper** — `blueprints/force-password-reset.yaml` forces a password change on next login for any user carrying `attributes.reset_password: true`, and `blueprints/users.generated.yaml` (generated by SecDeploy from `secsite.toml [[users]]`) gives each declared operator a random initial password with that flag set, rather than a shared or default credential. The generated file and its passwords are git-ignored (see repo `.gitignore`) | `blueprints/force-password-reset.yaml`, `blueprints/users.generated.yaml` |
| IA | — | Non-repudiation of initial credential issuance | **Wrapper** — `state: created` on generated users means an operator's password change is never silently overwritten by a later blueprint re-apply (create-once semantics) | `blueprints/users.generated.yaml` (header comment), README.md § "Onboarding users" |

## 3.1 Access Control (AC)

| Family | Control | Requirement | Implementation | Evidence |
|---|---|---|---|---|
| AC | 3.1.1 / 3.1.2 | Limit system access to authorized users / transactions | **Upstream** — deny-by-default login; every application requires an authenticated session. **Wrapper** — admin-plane access to downstream consoles is additionally gated on IdP group membership, not just "is a valid SecSSO user": `secllm-admins` (created by `blueprints/secllm.yaml`, checked by SecLLM's `SECLLM_ADMIN_GROUP`), and `secrouter-admins` / `secchat-admins` (created and populated by `blueprints/users.generated.yaml`, checked by the respective consoles) | `blueprints/secllm.yaml` (`group-secllm-admins`), `blueprints/users.generated.yaml` (group entries + user `groups:`) |
| AC | 3.1.5 | Least privilege / separate duties by identity | **Wrapper** — each suite integration gets its own `client_id` and grant type scoped to what it actually does, instead of one shared credential: public PKCE clients for interactive human sign-in (`secrouter-oidc.yaml`, `secrouter-admin-console.yaml`, `secchatng.yaml`, `secllm.yaml`, `secrecorder.yaml`), a public device-code client for CLI login (`secagent-pi.yaml`), and confidential `client_credentials` clients for headless service calls (`secagent-service.yaml`, `secchat-service.yaml`). A shared `secrouter` audience scope mapping (`secagent-audience.yaml`) is applied only to the providers that actually need to call SecRouter | `blueprints/secagent-audience.yaml`, and each provider blueprint listed |
| AC | 3.1.10 / 3.1.11 | Session lock / termination | **Upstream** — Authentik's configurable session policies (timeout, lock). **Wrapper** — every OAuth2 provider blueprint wires an explicit `invalidation_flow: default-provider-invalidation-flow`, not merely the default, so RP-initiated logout is available suite-wide (e.g. `secchatng.yaml` also registers its `post_logout_redirect_uri` so the BFF's logout actually lands back on the app) | every `blueprints/*.yaml` provider entry's `invalidation_flow`; `blueprints/secchatng.yaml` (logout redirect URIs) |
| AC | 3.1.12 / 3.1.13 | Control & encrypt remote access | **Wrapper (config guidance)** — operators are directed to run behind a TLS-terminating reverse proxy or Authentik's built-in `:9443`, and to set `SECSSO_EXTERNAL_URL` to the `https://` origin so the OIDC issuer and every blueprint's redirect URI matches what's actually served | `docs/production.md` § "TLS & external URL", § "Hardening" |
| AC | 3.1.3 | Control the flow of CUI | **Gap (out of scope here)** — SecSSO issues identity only; CUI flow/egress control is enforced at SecRouter, not at the identity layer | delegated — see `work/secrouter/docs/compliance/cmmc-control-matrix.md` § 3.1 |

## 3.3 Audit & Accountability (AU)

| Family | Control | Requirement | Implementation | Evidence |
|---|---|---|---|---|
| AU | 3.3.1 | Create & retain audit records | **Upstream** — Authentik maintains its own built-in event log (`authentik_events.event`) covering logins, admin/model changes, and flow execution, independent of anything this repo configures | Authentik admin → Events; Authentik's own Events documentation |
| AU | 3.3.2 | Trace actions to individual users | **Upstream** — Authentik event records carry the acting user/actor | Authentik admin → Events (per-record actor) |
| AU | 3.3.7 | Authoritative, time-synced timestamps | **Upstream** — Authentik timestamps events in UTC. **Shared** — accuracy depends on host NTP, which is environment-owned (see [Shared responsibility](#shared-responsibility)) | Authentik admin → Events; host NTP config |
| AU | 3.3.8 | **Protect audit information** (tamper evidence) | **Gap** — Authentik's event log is a plain relational table; it is **not** hash-chained the way this suite's other local audit stores are (SecRouter's `store/sqlite.ts` `chainHash`/`verifyAuditChain`, per B.2 of this suite's audit contract). A row can be edited or deleted at the database layer without a chain-verify catching it. Mitigate at the environment layer: restrict direct Postgres access, and ship events to an external, append-only sink (see Shared responsibility) | none in this repo — explicitly listed as a gap |
| AU | 3.3.9 | Limit audit management to a subset of users | **Upstream** — the Events log is only reachable through the Authentik admin interface, itself gated by admin role | Authentik admin role/permissions |
| AU | — | Per-event evidence export (B.6-shaped bundle) | **Gap** — SecSSO does not implement a `secsso evidence` command or an `/admin/api/evidence`-style endpoint; there is no self-assessment/evidence-bundle tooling here (unlike SecRouter, SecChat, SecAgent, SecLLM per the suite's audit contract). Operators needing exported events must use Authentik's own admin UI/API directly, or forward events to a SIEM | none in this repo — explicitly listed as a gap |
| AU | — | **CUI-safe logging** | **Upstream** — Authentik's event log records identity/administrative metadata (who, what action, when); it does not log request bodies or application content, since SecSSO never sits in any suite component's data path | N/A — SecSSO is not on the CUI request path |

## FIPS / accreditation posture

> **Verbatim from `docs/production.md`:**
> "Authentik's cryptography is **not** FIPS-validated. In a FIPS/CMMC enclave, federate the
> suite to an **existing accredited IdP** (the `--without secsso` path) rather than making
> SecSSO the identity authority. SecSSO is the right fit for evaluation, lab, and lower
> environments, or where a validated IdP isn't required."

This is the single most important line in this document for an assessor: **do not list
SecSSO as the identity authority on a CMMC L2/L3 SSP.** Concretely:

- **When SecSSO is appropriate as identity authority:** evaluation, development, lab, and
  non-CUI/lower environments — anywhere a validated cryptographic module is not a control
  requirement.
- **When it is not appropriate:** any environment where 3.13.11 (FIPS-validated cryptography)
  is in scope. There, federate the suite to an existing accredited IdP (Okta, Entra,
  Keycloak, Ping — see README.md § "Already have an IdP? Drop SecSSO.") and deploy with
  SecDeploy's `--without secsso` path. The blueprints in this repo remain useful as a
  reference for what to configure on that external IdP (same OIDC apps, same `groups`
  scope, same audience wiring), but the running Authentik instance itself is not present in
  that topology.
- SecCert carries an equivalent, independent non-FIPS caveat for the suite's other
  optional "identity & trust" component (certificate issuance) — the two are deliberately
  parallel: both are the "you have nothing yet" path, both are dropped identically when a
  validated alternative already exists.

## Suite integration

SecSSO issues OIDC tokens; it does not consume or enforce them itself. How downstream
components use what SecSSO issues:

- **`sub` as principal.** Every suite verifier treats the token's `sub` claim as the
  authenticated principal. SecRouter's `OidcProvider.authenticate` (`work/secrouter/src/security/identity/oidc.ts`)
  builds its internal `Principal.id` directly from `sub` after signature/issuer/audience
  verification.
- **`amr`/`acr` MFA claims.** Whether a user's session actually performed MFA is asserted
  upstream by Authentik's authentication flow (see IA 3.5.3 above) and carried in the
  token's `amr`/`acr` claims. SecRouter's `requireMfa`/`requiredAcr` config gate reads those
  claims in the same `authenticate()` method and rejects sign-in when they're absent —
  SecSSO's job ends at emitting the claim; the enforcement is entirely SecRouter's.
- **Service accounts via `client_credentials`.** Non-interactive suite callers authenticate
  as their own NPE identity rather than borrowing a user's token: `blueprints/secagent-service.yaml`
  and `blueprints/secchat-service.yaml` provision confidential `client_credentials` providers
  for this (see those files' headers for the exact `sub` each grant produces — notably
  SecChat's requires a pre-provisioned service-account user + app-password to get an exact
  `sub`, documented in `secchat-service.yaml`'s "Getting an exact sub" section).
- **The delegated `X-Sec-Acting-User` pattern happens at SecRouter, not here.** SecSSO has
  no concept of "act as another user" — it issues one token per authenticated identity.
  On-behalf-of delegation (a trusted service forwarding an end-user's identity via the
  `X-Sec-Acting-User` header) is implemented and gated entirely in SecRouter's
  `applyDelegation()` (`work/secrouter/src/security/identity/oidc.ts`), restricted to exact
  `sub`s enumerated in `security.oidc.delegatingSubjects`. SecSSO's only relationship to
  that mechanism is that it is the IdP that issued the trusted service's own token in the
  first place.
- **Groups → per-group policy.** The `groups` scope mapping (defined once in
  `blueprints/secrouter-oidc.yaml` as `scope-groups`, reused by `secrouter-admin-console.yaml`
  and requested by `secchatng.yaml`/`secllm.yaml`/`secrecorder.yaml`) puts the user's
  Authentik group names in the token; downstream components map those names to their own
  policy (SecRouter's `security.policy.groups`, SecChat's/SecLLM's admin-group checks).

## Shared responsibility

SecSSO enforces identity-layer configuration. The surrounding environment must still
provide:

- **Postgres backups.** Authentik's Postgres database is the source of truth for users,
  groups, flows, and every applied provider/application object — the blueprints only
  reconcile what they declare, not manual edits or user-created state. Back it up on a
  schedule (`docs/production.md` § "Backups"; `bootstrap/secsso.sh backup`/`restore`).
- **Log retention / shipping.** Authentik's event log (AU 3.3.1) has no built-in long-term
  retention policy or SIEM forwarder configured by this repo. Retention, off-box shipping,
  and review cadence are environment-owned.
- **NTP.** Accurate event timestamps (AU 3.3.7) depend on host time sync, not anything
  SecSSO configures.
- **Host FIPS mode / validated cryptography.** As covered above, Authentik's own crypto is
  not FIPS-validated; a FIPS-mode host does not change that. The environment's
  responsibility here is to keep SecSSO out of the identity-authority role entirely when
  3.13.11 is in scope, and to run the accredited external IdP the suite federates to
  instead.
- **Network segmentation.** Restricting access to the Authentik admin interface and to
  Postgres/Redis to an internal segment (`docs/production.md` § "Hardening") is a
  deployment-topology responsibility, not something the blueprints enforce.
